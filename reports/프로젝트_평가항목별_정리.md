# 아기캥거루(4팀) 프로젝트 — 평가 항목별 정리

**주제**: 경구약제(알약) 객체 탐지
**파이프라인 구조**: 데이터 전처리 → 통합 파이프라인(학습) → 모델별 평가 → Kaggle 제출

---

## 1. 데이터 전처리 및 탐색

### 1-1. 문제 해결에 필요한 데이터를 적절히 수집하였나요?

**수행 내용**

Kaggle 제공 원본만으로는 학습 데이터가 부족하다고 판단해 외부 데이터를 추가 확보했다.

| 구분 | 이미지 | 객체 | 클래스 |
|---|---|---|---|
| Kaggle 원본 | 232 | 763 | 56 |
| AI-Hub 추가분 | 11,964 | 45,631 | 116 |
| **통합 결과** | **12,196** | **46,394** | **118** |

- 원본 대비 이미지 **52배**, 객체 **60배** 확보
- 두 출처의 클래스 체계가 달라 단순 병합 시 172개 클래스가 되는 문제를 확인하고, 동일 약품을 가리키는 **중복 클래스 54개 그룹을 병합**해 118개로 정리
- 출처 구분을 위해 파일명에 `base__` / `extra__` 접두사를 부여해 추적 가능성 확보
- 추론 전용 이미지 842장(라벨 없음)을 별도 분리해 학습 데이터와 혼입 방지

**강점**: 데이터 부족이라는 문제를 인식하고 외부 데이터로 해결했으며, 병합 과정에서 발생하는 클래스 중복 문제까지 처리했다.

**보완점**: AI-Hub 데이터의 라이선스·사용 조건을 보고서에 명시하면 좋다.

---

### 1-2. 충분한 데이터 전처리 과정을 진행하였나요?

**전처리 파이프라인 (모든 이미지에 동일 적용)**

```
EXIF orientation 정규화
  → ICC-aware sRGB 색공간 변환
  → bilateral filter 노이즈 제거 (d=5, sigmaColor=20, sigmaSpace=20)
  → clipped gray-world 화이트밸런스 (gain 제한 ±0.05)
  → LAB L채널 전용 CLAHE (clipLimit=1.5, grid 8×8)
  → 종횡비 보존 letterbox 960×960 (padding = 테두리 중앙 RGB)
  → BBox 좌표 동기 변환 및 재검증
```

설계 의도가 명확한 선택들:
- **CLAHE를 L채널에만** 적용 — 색상 왜곡 없이 각인 대비만 강화
- **화이트밸런스 gain 제한** — 과보정으로 알약 색상 정보가 손상되는 것 방지
- **letterbox padding에 테두리 중앙값 사용** — 검정 padding이 만드는 인위적 경계 회피

**품질 검증 (자동화된 게이트)**

| 검사 | 방식 | 결과 |
|---|---|---|
| 좌표 유효성 | 엄격한 경계 검사 + float 잔차만 허용(0.01px) | 위반 0건 |
| 클래스 충돌 | 동일 BBox에 다른 클래스 (IoU ≥ 0.95) | 74건 검출 |
| 그룹 형태 이상치 | 클래스-그룹별 robust z-score | 543건 검출 |
| 촬영그룹 일관성 | 그룹 내 클래스 시그니처 비교 | 152건 검출 |
| Train/Val 누수 | 4,104개 그룹의 split 교차 검사 | **0건** |
| 계약 검증 | 이미지/객체/클래스/그룹 수 assertion | 전항목 통과 |

**EDA**

- 클래스 불균형(최대/최소 객체 비율), 클래스별 이미지·그룹 수
- **학습 해상도 진단** — 640/960/1280에서 BBox 짧은 변의 실제 픽셀 크기와 16px 미만 비율 계산 → imgsz 선택의 정량 근거
- BBox 규모 KMeans 군집 (silhouette로 k 선택)
- 위치 편향 분석 (촬영그룹 가중 Cramér's V)
- Train/Test domain shift (효과크기 + 신뢰구간 + FDR 보정, 색상은 원형 통계 사용)
- 근접중복 탐지 (dHash → pHash → SSIM → BBox 전경 SSIM → ORB 단계적 필터)
- 각인 가독성 시트 (640 vs 960 시각 비교)

**재현성 장치**

`group_contract_sha256`, `label_contract_sha256`, `config_sha256`, `PIPELINE_SOURCE_SHA256`를 산출물에 기록해, 다른 파이프라인이 동일 입력을 사용했는지 바이트 수준으로 대조 가능하도록 했다. audit 실행과 release 실행에서 `group_contract_sha256`이 동일하게 나온 것으로 재현성을 확인했다.

**강점**: 단순 리사이즈가 아니라 도메인 특성(각인 판독)을 고려한 처리 순서를 설계했고, 모든 단계를 자동 검증으로 감쌌다.

**보완점 (문서에 명시함)**
- 근접중복 스캔이 후보 상한 3,000건에서 중단되어 **Train/Test 누수 검사가 완전하지 않음** (`near_duplicate_scan_complete: false`)
- 마감 일정상 **육안 수동 검토를 생략**하고 769건을 유형별 자동 정책으로 승인 (근거는 `manual_review_decisions_v6_0.csv`의 note 컬럼에 기록)
- cross-class 충돌 74장은 계약값 유지를 위해 데이터셋에 포함하되 `training_exclusion_candidates.csv`로 별도 전달

## 2. 모델 선정 및 설계

### 2-1. 적절한 딥러닝 모델을 선택하고 설계하였나요?

**선택한 모델: YOLO11s / YOLO11m / YOLO12m (3종 비교)**

객체 탐지 과제이고 Kaggle 대회 지표가 mAP이므로 1-stage detector 계열이 적합하다고 판단했다. 세 모델은 두 축의 비교를 동시에 수행하도록 구성했다.

| 비교 축 | 조합 | 확인하려는 것 |
|---|---|---|
| 모델 크기 | YOLO11s ↔ YOLO11m | 파라미터 증가가 성능에 기여하는가 |
| 아키텍처 세대 | YOLO11m ↔ YOLO12m | 최신 세대가 이 도메인에서 유리한가 |

**설계상 핵심 결정: 세 모델이 완전히 동일한 데이터를 사용**

- 전처리 산출물 **1개**를 세 모델이 공유 (`data.yaml` 하나)
- 학습 데이터 staging 시 파일별 SHA256을 `dataset_manifest.csv`와 대조해 불일치 시 즉시 중단
- 모델별로 다른 것은 체크포인트(`yolo11s.pt`/`yolo11m.pt`/`yolo12m.pt`)와 하이퍼파라미터뿐

모델별로 데이터를 따로 만들면 성능 차이가 모델 때문인지 데이터 때문인지 구분할 수 없어 비교가 무의미해진다. 이를 코드 수준에서 강제했다.

**입력 해상도 960 선택 근거**

EDA의 `target_resolution_bbox_diagnostics.csv`에서 640/960/1280 각각에 대해 BBox 짧은 변 픽셀 크기와 16px 미만 비율을 계산했다. 알약 각인을 판독해야 하는 과제 특성상 640에서는 작은 객체의 각인이 뭉개지는 것을 시각 시트로 확인해 960을 선택했다.

**Train/Validation 분할 설계**

동일 알약 조합을 여러 각도(70°/75°/90°)로 촬영한 데이터라 무작위 분할 시 같은 촬영 세트가 train과 val에 나뉘어 성능이 과대평가된다. 이를 방지하기 위해 **촬영 조합 그룹(capture group) 단위 분할**을 적용했고, 4,104개 그룹 전부에서 교차 누수가 0건임을 검증한 뒤 그 분할을 고정해 사용했다.

---

### 2-2. 모델 설계와 선택 이유를 명확히 설명하고 있나요?

**근거가 명확한 부분**
- 입력 해상도 960 → EDA 정량 지표 + 시각 검증
- 그룹 단위 분할 → 데이터 촬영 구조에서 도출, 누수 0건으로 검증
- 단일 데이터셋 공유 → 공정 비교를 위한 통제변인 설정
- 증강 정책 → 알약 각인 판독성을 해치지 않도록 회전·색상 변형 범위 제한

**보완 필요 (보고서 작성 시 추가 권장)**
- **YOLO 계열을 선택한 이유**를 다른 detector(Faster R-CNN, RT-DETR 등)와 비교해 명시하면 좋다. 초기에 Faster R-CNN을 검토했다가 제외한 이력이 코드에 남아 있으므로, 그 판단 근거를 문서화할 것
- YOLO11**s/m** 두 크기만 쓰고 l/x를 제외한 이유(학습 시간·GPU 제약)를 명시

## 3. 모델 훈련 및 평가

### 3-1. 적절한 하이퍼파라미터 튜닝을 수행하였나요?

**실험 설계: 3모델 × 3단계 = 9개 실험**

| 단계 | 목적 | 주요 변경 |
|---|---|---|
| baseline | 기준선 확보 | epochs 6, batch 2, lr 0.005, 기본 증강 |
| tune_a | 학습량 확대 + 안정화 | epochs 14~16, lr 0.0025, safe_detection 증강 |
| tune_b | 정규화 조정 | epochs 17~19, weight_decay 0.0001, lr 조정 |

**데이터 규모에 맞춘 자동 조정**

12,196장 규모에서 원래 epoch 설정을 그대로 쓰면 학습 시간이 비현실적이므로, `LARGE_DATASET_EPOCH_SCALE = 0.4`로 축소하되 **실험 간 상대 차이는 유지**되도록 설계했다. 모델 크기에 따른 batch 상한(`{"s": 8, "m": 4}`)도 960px 기준 GPU 메모리에 맞춰 자동 적용된다.

**증강 정책의 도메인 특화**

알약 각인 판독이 핵심이므로 증강을 직접 통제했다. 특히 **albumentations가 설치만 되어 있어도 Ultralytics가 Blur/CLAHE 등을 임의로 적용하는 문제**를 발견해 패키지 자체를 제거했다. 회전 ±15°, 이동 ±8%, 스케일 0.90~1.10, hue shift ±3 등으로 범위를 제한했다.

**추론 정책 탐색**

학습 하이퍼파라미터 외에 **confidence × Top-K 조합을 Validation에서 그리드 탐색**했다. confidence 후보 8개(0.001~0.50) × Top-K 조합으로 대회 지표를 직접 최적화하고, 선택된 값을 `selected_confidence` / `selected_top_k`로 저장해 제출 단계로 전달한다.

**보완점**: 탐색이 수동 그리드 방식이다. Optuna 등 자동 탐색을 쓰지 않은 이유(GPU 시간 제약)를 명시하면 좋다.

### 3-2. 성능을 적절한 평가 지표로 평가하였나요?

**주 지표: mAP@[0.75:0.95]** — IoU 0.75, 0.80, 0.85, 0.90, 0.95의 평균

대회 규정 지표를 그대로 사용했다. 일반적인 COCO mAP50-95보다 **높은 IoU 구간만 평가**하므로 위치 정확도 요구가 훨씬 엄격하다. 알약처럼 작고 밀집한 객체에서는 박스가 조금만 어긋나도 점수가 떨어진다.

**보조 지표(진단용)**: COCO mAP50-95, mAP50, mAP75, precision, recall
**효율 지표**: inference_seconds, latency_ms_per_image

**평가 조건 통제**
- 고정 Validation 2,433장 (재분할 없음)
- `split_fingerprint`로 세 모델이 동일 split을 사용했는지 검증
- 체크포인트 manifest에서 `training_completed`, `model_name` 확인 후 평가
- CUDA 워밍업 시간을 추론 시간 측정에서 제외

**결과 (2026-08-18 기준)**

| 실험 | 소요 | mAP@[0.75:0.95] |
|---|---|---|
| yolo11s_baseline | 1:27:13 | 0.9742 |
| yolo11s_tune_a | 3:15:11 | 0.9779 |
| yolo11s_tune_b | 4:43:37 | **0.9790** |
| yolo11m_baseline | 2:02:10 | 0.9755 |
| yolo12m_baseline | (진행) | 0.9711 (4에폭 시점) |

**보완점 — 반드시 검토 권장**

mAP@[0.75:0.95] 0.97대는 118클래스 탐지에서 이례적으로 높다. 전처리 audit에서 `train_cross_group_near_duplicate` **292건이 미검토 상태**로 남아 있는데, 이는 "서로 다른 촬영 그룹인데 이미지가 거의 동일한 쌍"이다. 이 중 일부가 train과 val로 갈라졌다면 사실상 누수이며 성능이 과대평가된다.

검증 방법: `near_duplicate_candidates_raw.csv`에서 `high_priority=True`, `pair_scope='train_train'`인 쌍을 추출해 `dataset_manifest.csv`의 `split` 값이 서로 다른 경우를 집계한다. **발표에서 "왜 이렇게 높은가"라는 질문에 답할 근거가 되므로 확인을 권장한다.**

### 3-3. 성능 개선을 위해 다양한 시도를 하였나요?

| 시도 | 내용 | 결과 |
|---|---|---|
| 데이터 증강(수집) | Kaggle 232장 → 12,196장 | 학습 데이터 52배 |
| 클래스 정리 | 중복 54개 그룹 병합 (172→118) | 라벨 일관성 확보 |
| 이미지 품질 개선 | denoise + WB + CLAHE | 각인 대비 향상 |
| 해상도 실험 | 640/960/1280 정량·시각 비교 | 960 선택 |
| 3모델 비교 | 크기 축 + 세대 축 | 진행 중 |
| 단계별 튜닝 | baseline → tune_a → tune_b | 11s 기준 0.9742 → 0.9790 |
| 추론 정책 최적화 | confidence × Top-K 그리드 | 모델별 최적값 도출 |
| 증강 통제 | 각인 보호를 위한 범위 제한 | 도메인 특화 |
| 오프라인 증강 | BBox-safe 증강 생성기 구현 | 부가 기능으로 준비 |

**개선 폭**: YOLO11s에서 baseline 대비 tune_b가 +0.0048 (0.9742 → 0.9790). 이미 높은 구간이라 절대 상승폭은 작지만, 오차 구간이 아니라 일관된 개선 방향을 보였다.

**보완점**: 앙상블(모델 3종 결합), TTA는 코드에 스위치만 준비되어 있고 실제 적용·검증은 하지 않았다. 시간이 허락하면 시도 가치가 있다.

## 4. 코드 품질 및 문서화

### 4-1. 코드가 가독성과 유지보수성을 고려하여 작성되었나요?

**강점**

1. **계약 기반 설계** — 각 단계가 기대값을 assertion으로 명시한다. 이미지/객체/클래스/그룹 수가 어긋나면 잘못된 산출물을 만드는 대신 즉시 중단한다.

2. **2-pass 실행 모델** — `audit`(검토 자료만 생성) / `release`(품질 게이트 통과 시에만 최종 산출물 생성)로 분리해, 검증 없이 데이터가 나가는 것을 구조적으로 차단했다.

3. **원자적 게시** — staging에서 전부 만들고 검증한 뒤 교체한다. 기존 산출물을 먼저 지우지 않고 backup으로 옮긴 후 교체하며, 실패 시 자동 복구한다.

4. **설정 중앙화** — 경로·임계값·정책이 한 셀에 모여 있어 환경 이전 시 그 셀만 수정하면 된다. 실제로 Kaggle 이전 시 이 구조가 유효하게 작동했다.

5. **환경 대응** — Google Drive FUSE 연결 끊김(Errno 107)에 대한 자동 재마운트·재시도, 대용량 아카이브 지문 캐싱 등 실행 환경의 불안정성을 코드로 흡수했다.

6. **재현성 지문** — 설정·라벨·그룹 정의를 각각 해시로 기록해 다른 실행/다른 파이프라인과 대조 가능하다.

**보완점**

- **모놀리식 노트북** — 전처리 노트북이 166셀에 전처리·EDA·중복탐지·통계검정·시각화·export·증강을 모두 포함한다. 한 부분이 실패하면 전체를 다시 실행해야 한다. 모듈 분리가 바람직하다.
- **전처리 ↔ 제출 파이프라인 스키마 불일치** — 제출 파이프라인이 구버전(232장/56클래스) 산출물을 기대하도록 남아 있어 연동이 되지 않는 상태다. (별도 진단 문서 작성 완료, 어댑터로 해결 예정)
- 원본 학습 노트북(`박단비_YOLO12m_Competition_Train_V1_1.ipynb`)에 미완성 경로로 인한 SyntaxError가 남아 있다.

### 4-2. 코드 내 주석 및 마크다운이 잘 작성되어 있나요?

**강점**

1. **섹션 구조화** — 22개 섹션으로 논리 단계를 나누고, 각 섹션마다 마크다운으로 목적과 산출물을 명시한다. 전체 진행률과 현재 단계를 함께 표시한다.

2. **"왜"를 설명하는 주석** — 단순히 코드를 재서술하는 대신 판단 근거를 남겼다.
   ```python
   # IntegratedDataset은 파일명에 base__/extra__ 접두사가 붙어 있어서
   # derive_group_id(첫 토큰 분리)를 그대로 쓰면 접두사만 group_id로 잡혀
   # 전체가 'base'/'extra' 단 두 그룹으로 뭉개진다.
   ```
   ```python
   # YOLO→픽셀 변환의 부동소수점 잔차만 흡수하는 허용치(px).
   # 실측 잔차는 1e-6~1e-5px, 6자리 반올림 라벨의 이론적 최대 잔차도 약 1e-3px이므로
   # 0.01px이면 충분하다. 이 범위를 넘는 이탈은 실제 라벨 오류이므로 검증에서 그대로 잡는다.
   ```

3. **산출물 자체 문서화** — `DATASET_CARD.md`에 데이터 규모·전처리 내역·사용 규칙과 함께 **Known limitations 섹션**을 두어, 육안 검토 생략·근접중복 스캔 미완료·제외 후보 74장을 명시했다. 한계를 숨기지 않고 다음 단계 담당자가 판단할 수 있게 했다.

4. **의사결정 이력 보존** — 적용되지 않는 legacy 코드에 "왜 남겨두는지"를 명시했다.
   ```python
   # [FIX 11] 주의: 아래 CURATED_BBOX_FIXES는 이 번들에서 구조적으로 절대 적용되지 않는다.
   # (a) annotation id를 100,000,000 offset부터 새로 부여하므로 옛 id와 만날 수 없고,
   # (b) 파일명에도 base__ 접두사가 붙어 옛 파일명과 매칭되지 않는다.
   # 이력 보존용으로만 남겨둔 값이며 '이번 실행에서 보정이 적용된다'고 읽으면 안 된다.
   ```

5. **주석 정리** — 자동 생성된 무의미한 보일러플레이트 주석 1,743줄을 제거하고, 판단 근거가 담긴 주석만 남겼다. 파일 크기 1,365KB → 330KB.

### 회고

이번 프로젝트에서 가장 크게 배운 것은 **"에러 없이 조용히 틀리는 문제가 가장 위험하다"** 는 점이다.

실제로 `class_mapping.csv`의 `original_category_id` 컬럼에 원본 ID가 아닌 YOLO 인덱스가 들어가는 버그가 있었다. 프로그램이 죽지 않아 정상 산출물처럼 보였지만, 이 파일은 Kaggle 제출 시 클래스 ID를 되돌리는 데 쓰이므로 그대로 나갔다면 제출 결과가 통째로 어긋났을 것이다.

또 부동소수점 오차를 정리하려고 넣은 clamp가 범위가 너무 넓어, 크게 잘못된 라벨까지 정상으로 바꿔 후속 검증을 통과시키던 문제도 있었다. **품질 검사 코드가 오히려 품질 문제를 은폐할 수 있다**는 것을 경험했다.

이런 문제들은 실행이 성공했다는 사실만으로는 발견되지 않는다. 산출물을 직접 열어 값을 확인하는 과정이 반드시 필요하다는 것을 배웠다.
